# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

献祭 (Xianni) — a Vampire Survivors-style roguelike survival game (MVP). Phaser 3 + Vite + TypeScript, entirely client-side. UI text and code comments are in Chinese; match that when adding user-facing strings or comments.

Theme: a cultivation (修仙) reskin based on the novel 《仙逆》. Spells (法术) are the attacks, relics (遗物) shape the build, and XP is cultivation (修为) spent on level-ups (悟道三选一).

The three design docs under `docs/` are the source of truth for numbers and rules:
`build设计.md` (spells / relics / evolutions / card pool), `地图设计.md` (maps + hazards +
boss schedule), `怪物设计.md` (enemy tiers and behaviour). When code and doc disagree, the doc wins.

## Commands

```bash
npm run dev        # dev server on http://localhost:5173 (open=false, browser not auto-launched)
npm run typecheck  # tsc --noEmit — the only real correctness gate
npm run build      # typecheck + vite build to dist/
npm run preview    # serve the production build
npm run icons      # regenerate public/icons/*.png (see Mobile below)
```

There is no test suite, linter, or formatter configured. `tsconfig.json` is strict with `noUnusedLocals`/`noUnusedParameters`, so unused variables/imports fail the build.

## Architecture

Scene flow (each scene registered in the `scene` array in `src/config/GameConfig.ts`):

`BootScene` → `PreloadScene` → `MainMenuScene` → `GameScene` (launches `UIScene` in parallel; `UpgradeScene` on level-up and on every chest pick; `GameOverScene` on death). `ReplaceSpellScene` was deleted — with 5 spells and 5 slots there is nothing to replace.

`GameScene` is the orchestrator and owns all cross-system wiring. Systems are plain classes constructed with explicit dependencies — they never reach for globals.

Key conventions:

- **Pooling is Phaser Groups with a finite `maxSize` and explicit `classType`.** This is not optional. Phaser's `Group` defaults to `maxSize: -1`, and `isFull()` returns `false` unconditionally in that case — so an exhausted pool's `get()` does *not* return null, it constructs a bare `Sprite` with a null texture. The subsequent `setup()` throws a `TypeError` and the object leaks permanently. With a finite `maxSize`, `get()` correctly returns null and the existing `if (!e) return;` guards work. Pool sizes and prewarm counts live together in `GameScene.setupPools()`.
- **Pooling return is inconsistent by entity type.** `Projectile.kill()` and `Pickup.kill()` deactivate themselves; enemies are only deactivated in the death tween's `onComplete`. New pooled entities should follow the `kill()` + `isDead` flag pattern (`isDead` guards both overlap callbacks and enemy-iteration loops).
- **Reuse requires total state reset.** Every pooled entity's `setup()` resets all mutable fields. Missing resets show up as a projectile keeping a stale `hitSet`, or an elite's `scale`/`alpha` bleeding onto the next normal enemy.
- **Physics bodies must be toggled explicitly.** `setActive(false)` does not disable an Arcade body. Every `kill()` must set `body.enable = false` + zero velocity, and every `setup()` must set `body.enable = true` — otherwise a recycled pickup silently never gets collected.
- **Never tween a pooled object.** `pauseGame()` calls `tweens.pauseAll()`, and a tween still in flight when the object is recycled will fire on whoever owns it next. Use a numeric field decayed in `preUpdate()` instead (see `Projectile.chainGlowMs`).
- **Guard all `preUpdate()` methods with `this.scene.physics.world.isPaused`.** `preUpdate` is driven by the scene UPDATE event, not physics, so pausing physics does *not* stop it — without the guard, HP regen ticks during the upgrade panel and in-flight projectiles expire.
- **The UI is pull-based, not event-driven.** `UIScene` receives no event payloads; events are only refresh signals. Real data comes from `this.scene.get('GameScene') as any` reading public fields. So a new system just needs public fields on GameScene plus an event for HUD refresh. `UIScene.update()` refreshes the HUD every frame (the timer otherwise freezes between events).
- **`GameScene.create()`'s last line is `scene.launch('UIScene')`.** UIScene's `create()` runs after GameScene constructs its systems, so **every new system must be built in `setupSystems()`, never below that line**, or the HUD reads `undefined`.

### Cultivation systems

- **Realm state is split, not merged into `XPSystem`.** `XPSystem` owns only `xp`/`level`/`xpToNext` and knows nothing about realms. `RealmSystem` is a pure **buff ladder**: each level-up advances a minor stage, and crossing a major boundary multiplies `hpMul`/`speedMul` and emits `BREAKTHROUGH`.
- **Realms no longer gate anything.** The old key-item (丹药) requirement, `canAdvanceLevel` gate and `isBlocked` HUD state are gone — the build design's chain is 灵气 → 等级 → 悟道 → 宝箱 → 融合, with no potion in it. `player.maxHealth` is now a **pure function** (`BASE_MAX_HEALTH × realm.hpMul × relic.maxHealthMul`) computed in `GameScene.syncPlayerStats()`. Never multiply into `player.maxHealth` directly — the relic term would be applied twice on the next recompute.
- **XP curve is `0.9 × L^1.75` rounded to 5s** (`XPSystem.computeXpToNext`). It is the single most important tuning number; the build doc's table matches it point for point and targets level 60–75 in a 30-minute run. If pacing feels off, drop the exponent to 1.65 — **do not raise slot counts to compensate**.
- **`XPSystem.add()` levels up exactly once per call.** `onLevelUp` pauses and launches `UpgradeScene`; a second `launch()` on a running scene is a no-op, so continuing the loop would silently swallow surplus levels. `GameScene.processPendingLevelUps()` drains the remainder after the card is chosen.
- **The insight card pool is built by `GameScene`** (`buildInsightCards` + the `cards*` producers), not by a config file. Only GameScene holds all systems and knows whether a slot is free. `UpgradeScene` stays a dumb renderer over `data.cards`.
- **The 6th slot (化神 onwards) is deliberate headroom, not an oversight.** With only 5 spells, 元婴 already lets you hold everything, so the HUD reads 法位 5/6 forever. That was a decision, not a bug: a 6th spell would slot straight in with no realm-table change, an empty slot keeps reading as "there is another road" instead of "you have no choice left", and收槽 would mean inventing a separate 化神 reward. Don't "fix" it.
- **Spell slots are a realm ladder, not a constant.** `RealmConfig.spellSlots` is the single source of truth: **2 at 凝气, +1 per major realm through 化神 (3/4/5/6)**. `RealmSystem` pushes it into `WeaponSystem.setSlotCap()` at construction and on every breakthrough — WeaponSystem must not import `REALMS`. The ladder is what makes "which two roads do I commit to" a real question in the first 16 levels, since there are 5 spells. `cardsNewSpell()` returns `[]` once the cap is reached, so the `newSpell` category silently drops out of the weighted draw until the next breakthrough opens a slot.
- **`debugGrantAllSpells`/`debugNextSpell` iterate `BASE_SPELL_IDS`, never `Object.keys(SPELLS)`.** Handing out an evolved form from the debug panel makes the fusion chain look healthy while normal play can never reach it — the same failure `validateEvolvedNotOffered` guards against. Use `凑齐融合` to inspect evolved forms.
- **Cards are drawn by category, not by item.** `CARD_WEIGHTS` (新法术 30 / 法术升级 22 / 新遗物 25 / 遗物叠层 13 / 消耗品 10) picks a category that still has stock, then a random item from it. Drawing items directly would make the one un-learned spell show up 1-in-5 instead of reliably appearing. There is also a guaranteed "not yet owned" card while a slot is free, and a consumable fallback so the panel is never empty.
- **`Upgrade.apply` takes an `UpgradeContext`, not a `Player`** — it carries `damageAllEnemies` and `addCoins` so consumables (清屏符 / 灵石袋) route through GameScene's unified entry points. `src/config/UpgradeConfig.ts` (the deprecated shim) was deleted.

### Spells and relics

- **`SpellConfig` spells out every level.** Each row is a `SpellLevel` with final values — no base value × curve. The build doc's tables change shape *and* numbers at levels 3/5/8 (厚土术's level 5 adds a segment and a target-cap), which a single multiplier cannot express. `resolveSpell(id, level)` converts grids→px and seconds→ms in one place; nothing else does unit math.
- **Evolved forms have exactly one row.** `resolveSpell` clamps to the row count, so the level a spell carries through fusion stops mattering — which is the other half of "fusion absorbs the exclusive relic": the levels have already paid out.
- **⚠️ In-place transformation breaks every "do I already have X?" check.** `evolve()` rewrites `spell.id` and `absorb()` removes the relic, so after fusion `hasSpell('fireball')` and `has('tianni_ye')` are both **false** — and whatever asked that question will happily hand the player their own starting spell back. Both pools hit this: the base spell re-entered `newSpell`, and the absorbed key relic re-entered `newRelic` (where it does nothing at all, since `RelicSystem` only applies an exclusive relic when `exclusive === spellId`, and the spell id is now the evolved one). The guards live at the source, not at each call site: `WeaponSystem.hasEvolvedForm()` is checked inside `addSpell()` (one entry point) and `EvolutionSystem.isRelicSpent()` inside `cardsNewRelic()`. Any future in-place transformation needs the same treatment.
- **The insight panel always returns exactly three cards.** Cards are drawn by category but the categories are *not* de-duplicated — only the drawn card is spliced out. An earlier `usedTypes` set ("one card per category, for variety") meant that once a category emptied out (all spells maxed, relic bar full) the panel could only assemble **two** cards, and the player saw a two-option "三选一" with no explanation. Consumables are the designed endless fallback ("法术与遗物全满后只出消耗品") and top the panel up to three.
- **Debug buttons must not be able to fail silently.** `凑齐融合` equipped the key relics through `relicSystem.equip()`, which returns `null` when the 6 slots are full — the most common state by mid-run — so the button reported "条件不满足" and the entire evolution chain became unreachable from the panel. It uses `debugEquip()` (cap-ignoring, level-5) now. A debug path that can fail is a content path you cannot verify.
- **Fusion bakes the exclusive relic's numbers into the evolved row.** The relic is *absorbed* (that is what frees a slot), so anything the row does not carry is a permanent downgrade — 斩罗决's `count: 8` is 仙剑's 8 swords written into the row, not "6 + a bonus that no longer exists". Design doc's 273 DPS for 斩罗决 only closes with 8, and the player must not watch their sword count drop on the turn they fused.
- **`RelicSystem` returns two different shapes.** `getSpellMods(spellId)` is per-spell (exclusive relics only apply to their own spell), `getPlayerMods()` is global. Do not collapse them into one object: the "is this global or per-spell" question would then have to be asked every frame.
- **Fusion is judged in `EvolutionSystem`, paid in `ChestSystem`.** Condition = spell at 8 + exclusive relic at 5; the fusion only happens on the *next* chest, and `GameScene.processPicks()` checks it **before** `takeOne()` so it does not consume a reward pick (build doc 3.5 rule 2). `EvolutionSystem.evolve()` also calls `relicSystem.absorb()`, which is what frees a relic slot — that is the payoff players feel.
- **`RelicConfig.mod(level)` is a function, not a table.** The relics' curves genuinely differ (天逆珠灵液 is linear +12%/level, 天逆珠 is ×0.95 per level, 储物袋 is additive +40%/level, 散魔铠甲's armor-pen only exists at level 5). `desc(level)` calls the same function, so card text can never drift from the real numbers.

### Attack forms

`SpellConfig.form` selects one of five forms, each with its own entity class in `src/entities/attacks/`:

| form | entity | hit resolution |
|---|---|---|
| `projectile` | `Projectile` (physics sprite) | Arcade overlap; `aim: 'target'` auto-locks, `aim: 'facing'` fires along the player's facing |
| `orbiter` | `Orbiter` (image) | proximity + per-hit cooldown (the cooldown *is* the orbit period) |
| `cone` | `SandWave` (container) | one sector query per advancing segment |
| `chain` | `ChainBolt` (container) | the whole chain resolves synchronously in `setup()` |
| `zone` | `Zone` (container) | periodic circular queries, stacks up to `maxStacks` |

The old `slam`/`arc`/`attractor`/`scan` entities were deleted along with the spells that used them.

- **The five geometries are pairwise distinct** (line / ring / fan / chain / lingering pool) — that is the build doc's "关闭特效只看碰撞体仍能一眼分辨" rule, and it is why a new spell must not reuse another's shape.
- **`ChainBolt` resolves instantly, on purpose.** 五雷正法's whole identity is "no flight time, cannot be dodged" versus 火球术's "has a landing point, can be dodged". It also scans for the next jump *before* returning, so a flying projectile could never chain more than once through a dense pack. The Graphics polyline it leaves behind is only a visual; the damage already happened.
- **`SandWave` deliberately has no `hitSet`.** One cast = N segments advancing outward, and an enemy that gets pushed outward passes through several of them, taking damage each time — that is the entire meaning of "分段推进" and the source of 厚土术's odd 36-single-target / 120-crowd DPS split. Adding de-duplication silently cuts its single-target damage to a third.
- **Chain lightning deals damage via `applyDamageToEnemy` like everything else** — the `element: 'thunder'` marker on `DamageOptions` is what lets 感电 amplify only thunder damage instead of every hit on a shocked enemy.
- **A projectile's hit radius is multiplied by its sprite scale, twice over.** `Body.setCircle` computes `width = radius*2 * _sx`, where `_sx` is the scale cached by the *previous* `updateBounds`; `updateBounds` then multiplies by the current scale again. So (a) the world radius is `radius × scale`, and (b) if you change `setScale` in the same call you must `body.updateFromGameObject()` **before** `setCircle` or that frame's hitbox uses the previous shot's scale. `Projectile.setup` therefore passes `hitRadius / visualScale`, which is how `SpellLevel.visualScale` widens the art without widening the hitbox — 化魔指's whole promise ("范围 ×5") is that pairing, and getting it wrong looks like "the hitbox is huge but the beam is a hairline".
- **`SpellLevel.clearsShots` is the 厚土术 capstone** and belongs to levels 8 and to 山崩地裂 — never to the early rows. The spell's single-target DPS is the lowest of the five (30); everything it buys is control (push, slow, wall), and clearing incoming fire is the *end* of that line ("push the monsters away" → "push the volley away"). At level 1 it would be a universal defensive card.
- **Boss attacks are immune to every form of clearing** (`EnemyShot.fromBoss`, set by `GameScene.spawnBoss`'s `spawnShot`). A boss's move set is its only source of pressure — if a sand wave could delete 朱雀's 火羽扇, the fight collapses into a damage race against a fat dummy. Any future "destroy enemy projectiles" effect must respect this flag.
- **`SpellLevel.note` exists so mechanic nodes are visible.** The design puts new mechanics at levels 3/5/8; without a note the upgrade card for those levels reads identically to a plain "+2 damage" card, and the mechanic only exists for whoever wrote the table. `cardsSpellLevel` shows the note in place of the damage delta whenever the next row has one.
- **Wide beams need their own `spreadRad`.** Three 128px bands fired into the default 0.16 rad fan just stack into one band; the player reads "范围 ×5" only if the three are visibly separate.

- **Every damaging form deals damage through `GameScene.applyDamageToEnemy`.** It is the single place that calls `enemy.takeDamage`, spawns the damage number, and triggers `onEnemyKilled`. Never call `enemy.takeDamage` directly from a new form. The two control forms are the exception by design: their `bind()` takes only the enemy group, so "this form is outside the damage chain" holds in the type signature.
- **Non-projectile forms are non-physics.** They're pure `GameObject`s driven by their own `preUpdate`, which works because `scene.add.existing()` adds any object defining `preUpdate` to the scene's update list (`GameObjectFactory.js:140`). Their pools use `runChildUpdate: false` — the `Group` calling `update()` would be pure overhead since these classes deliberately have no `update()`.
- **Their pool sizes equal their prewarm counts** so `Group.get()` can never construct an un-`bind()`ed instance. If you raise `maxSize`, raise the prewarm loop in the same edit, or a fired sand wave will crash on undefined `enemyGroup`.
- **`Orbiter` reads the player position through a `getPivot()` callback injected at `bind()` time**, not a captured coordinate. Capturing `player.x/y` in `setup()` looks correct and silently strands every orb behind a moving player — the whole point of the form is that it travels with you. `GameScene` supplies `() => ({ x: this.player.x, y: this.player.y })`.
- **Names that collide with Phaser base classes got renamed, not fought.** `angle` → `orbitAngle` (on `Image`), `body` → `seal` (on `Container`, which reserves `body` for physics).

### Damage, status and knockback

- **`GameScene.applyDamageToEnemy` is the single damage entry point**, and `DamageOptions` is the payload that carries armor penetration, burn, slow, shock and the `element` marker. Every status effect hooks here rather than in each form — a new attack form that forgets to apply them produces a "the spell says 30% slow but nothing slows" bug that only shows up in play.
- **Knockback is a velocity offset, never an impulse.** `EnemyAiSystem` rewrites every enemy's velocity in full each frame, so an impulse is erased on the next frame (this is exactly how the old 引力术 became a no-op). `Enemy.applyKnock()` writes `knockX/knockY/knockUntil`, and `applyStatusMotion()` adds them after steering and scaling by slow. `resistKnockback` short-circuits it.
- **Enemy armor is real.** `EnemyConfig.armor` (0–0.5) is subtracted in `applyDamageToEnemy`, and 破魔/破防 (`armorPen` on both `DamageOptions` and `SpellRelicMods`) is what pierces it. Without armor those two relic/evolution lines are pure flavour text.
- **DoT runs in `EnemyAiSystem.tickBurn`** (the second pass), not in `preUpdate`. It accumulates `burnDps × dt` and calls back into the damage funnel on whole numbers, so a fire tick can still kill, drop loot, and trigger 伪仙's death blast like any other damage.

### Container-based clickable cards (a bug we shipped once)

The cards in `UpgradeScene` are `Container`s holding a background rectangle plus text. Two ways to end up with a card that renders but cannot be clicked:

1. **Creating the background with `.setInteractive()` but never adding it to the container.** The rectangle stays on the scene's display list at world (0,0) — the *hit area strands in the corner* while the card shows nothing clickable. Whenever you build a card, verify the interactive object is in the `add([...])` list.
2. **Calling `container.setInteractive()` without `setSize()` + an explicit hit area.** A `Container` is 0×0, so the default hit area is a zero-area rect and nothing is clickable. Use `card.setSize(w, h)` then `card.setInteractive(new Phaser.Geom.Rectangle(-w/2, -h/2, w, h), Phaser.Geom.Rectangle.Contains)`.

Also note: a card that exists but is *rarely offered* is indistinguishable from a broken feature. `buildInsightCards()` guarantees a "not yet owned" card whenever a slot is free, for exactly this reason.

### Monsters (enemy-side design)

The enemy side is specified by `docs/怪物设计.md`, and its spine is that **each monster's approach geometry must differ from the others** — weapons have coverage shapes, enemies have approach shapes, and the gap between them is where positioning becomes a decision. All of it lives in `EnemyConfig.approach` and is executed by `src/systems/EnemyAiSystem.ts`.

- **`EnemyAiSystem` owns every enemy's velocity**, called from `GameScene.update()`. Frame order is `UpdateList` (all `preUpdate`s, inside UPDATE) → `World.update` (integration + overlaps) → `GameScene.update()`. The AI therefore always writes the *next* frame's velocity. Do not move steering into `Enemy.preUpdate`: which one wins would then depend on update-list insertion order.
- **`EnemyAiSystem.update()` runs three passes now**: steer → status motion (slow / knockback / stun) → field effects (shepherd drag, DoT ticks, wall blocking). Each pass is separate because later passes *add to* what earlier ones wrote; interleaving them is how you get "sometimes it works" bugs.
- **The opening is rule-bound, and the rule is enforced at boot.** `validateOpeningDifficulty()` checks two things the playtest settled: **(1)** no projectile-firing enemy (`approach` `ranged`/`flank`) before `FIRST_PROJECTILE_TIER` (currently T3 = 8:00) — the opening teaches movement and target selection, and a volley in the face teaches "stand still and tank" instead; **(2)** every enemy in T1 must die to **one** Lv1 starting spell, evaluated at the *end* of the window (the difficulty clock keeps raising HP until 4:00, so checking only t=0 under-tests it). The damage figure is read from `SPELLS[STARTING_SPELL].levels[0]`, never re-typed as a constant. Breaking either rule produces no error and no crash — only a worse opening — which is exactly why it is validated rather than remembered.
- **"Which enemy" and "how dense" are two independent tables.** `ENEMY_INTROS` says who first appears at which second (each with a `rampSeconds` so a new type arrives at 30% weight and thickens over the next minute or two); `PACE_SEGMENTS` says the base spawn interval and difficulty. They used to be one table, which coupled "introduce a second trash mob at 0:30" to "change density and HP scaling" — the four-minute step ladder was a product of that coupling.
- **⚠️ There are two clocks and they are not interchangeable.** `GameScene.elapsed` is ms since the *run* started; the `time` Phaser hands to `update()` is ms since the *page loaded*. Anything that schedules content from an absolute time must take `elapsed` — `SpawnSystem.update(seconds, …)` takes seconds for exactly this reason. It used to take `time`, which meant a player who sat on the main menu for 8 minutes got the 8-minute spawn table on the first second of their run while the HUD read 00:00. No error, no crash — just a run that opens with projectiles. Weapon cooldowns and `bornAt` may use `time` because they only ever compare two values from the same clock.
- **The opening is rule-bound and validated at boot.** `validateOpeningDifficulty()` enforces **(1)** no projectile-firing enemy (approach `ranged`/`flank`) before `FIRST_PROJECTILE_SECONDS` (8:00) — the opening teaches movement and target selection, and a volley in the face teaches "stand still and tank" instead; **(2)** every enemy introduced within `OPENING_SECONDS` (30s) must die to **one** Lv1 starting spell, evaluated at the *end* of the window because the difficulty clock keeps raising HP. The damage figure is read from `SPELLS[STARTING_SPELL].levels[0]`, never re-typed. `validateIntros()` checks the intro list itself (unknown ids, repeated ids, non-increasing times) — a reordered intro list silently shifts the whole schedule.
- **The monster doc's T1–T8 tiers are a label, not a mechanism.** `getTierAt()` maps seconds → tier purely so "we're in T4" can be said out loud; the actual schedule is the intro list. The enemy *roster* still predates the doc (山野妖兽/腐尸/散修…), so the doc's own T1 list (散修劫匪/阴魂/铁甲蚁/引气灵兔) is only partly covered — 铁甲蚁 was added to fill the opening's second slot.
- **Stealth (穿墙潜行) is a spawn rule, not a collision rule**: enemies have no terrain collision at all (obstacles only collide with the player), so the geometry only reads if the monster appears *inside* the screen (300–700px) at a random angle, semi-transparent. See `SpawnSystem.spawnOne`.
- **Resistances are merged, not overwritten**: `Enemy.setup` ORs `cfg.resist` (innate, e.g. a tank's 牵引抗性) with the elite roll. `rollEliteResists(base)` fills *up to* two total, so the doc's hard rule (never all three) holds even for a tank that already carries one.
- **`kill()` is the silent return path** (despawn at 1600px): no drops, no death tween, no damage number — the `Projectile`/`Pickup` pattern. `GameScene.killEnemy()` is the other one: full death funnel (drops, splits, kill count) but no damage number, used by 自爆.
- **HP × player realm** (`REALM_HP_SCALE`) is applied in `Enemy.setup`, the one place that sees realm index + difficulty + elite multipliers together.
- All behavior params (`attackRange`, `explodeRadius`, `splitInto`, `charge`, `pullSpeed`, …) are optional fields on `EnemyConfig`; only the matching approach reads them. Adding a monster = one row in `ENEMIES` — `AssetGenerator.generateEnemies` draws `enemy_${id}`/`elite_${id}` from `archetype` × the config's palette.
- **`approach: 'boss'` is a dispatch-only branch.** `bossSteer` runs the ordinary chase and then, when the boss's action timer comes up, calls `BossSystem.act()`. Bosses deliberately have *no* custom locomotion: their pressure must come from their **moves**, and giving them their own steering would split enemy balance into two systems.
- **A boss is a normal `ENEMIES` row with `boss: '<BossConfig id>'`.** Stats live in `ENEMIES` (one source of truth for art + numbers); moves and phases live in `BossConfig`. `Enemy.bossKey` is set from `cfg.boss` in `setup()`, so `EnemyAiSystem` never has to look at the boss table to know it should not despawn / teleport / be possessed by 寄魂.
- 秘境守 and 天运子 are **not** implemented — like the other five bosses and five maps, they are missing content, not missing code.

### Mechanism monsters (机制怪 + 伪宝匣)

Prototype monsters provide daily pressure; mechanism monsters provide the **exception** — each one invalidates a rule the player has been relying on. They are event spawns, not part of the wave table.

- **`MechanismSystem`** owns only the schedule (first at 70s, interval 85s→45s) and the roll (weighted, unlocked by realm, never the same one twice in a row). It dispatches through three injected callbacks because the three forms live in different places: `enemy` → `SpawnSystem.spawnChild`, `bait`/`mimic` → a `Pickup` on the ground, `tide` → a screen-level `BloodTide`. A screen hazard is not a monster and should not be forced into one.
- **Capabilities live in `EnemyConfig.mechanism`**, not in the AI: 追命者's `speedPerHit` is applied inside `Enemy.takeDamage` (that method is the only place that knows "damage happened" — a new attack form must not have to remember to notify it), 伪仙's `deathBlast` fires from `onEnemyKilled`, 遮天's `vignette` is read out of `EnemyAiSystem.veilActive` each frame so `GameScene` never has to scan the pool just to ask one question.
- **Field effects run in a second pass** (`EnemyAiSystem.applyDrag`). The shepherd's drag *adds* to neighbours' velocity, so it must land after every `chase()` — interleaved in the first pass, a neighbour that happens to sort later would have its drag overwritten, producing an "sometimes it works" bug that is miserable to find.
- **Additive pulls are velocity offsets (px/s), never `accel × dt`.** Enemy velocity is rewritten in full every frame, so an acceleration only ever acts for one frame (`accel × dt²` ≈ 0.1px). `pullSpeed` (界外之魂), the shepherd's drag and every spell knockback all add a velocity.
- 幻饵 (`bait`) and 伪宝匣 (`mimic`) are `Pickup` kinds that look identical to the real drop — that is their entire weapon, so they share the real textures. `mimic` copies the **gold** chest specifically. They trigger through the normal magnet+overlap path: you pull them in yourself.

### Maps, hazards and bosses

- **`MapConfig` describes a map, `HazardSystem` interprets it.** A map is world size + ground palette + one `HazardDef`. 朱雀星's `lingmai` is the `kind: 'vent'` implementation: pick a point near the player → warn (a shrinking ring) → erupt. **The warning is the mechanic** — without it the columns are random damage; with it, they are a positioning question, which is what the map doc asks for. Future maps add a `kind` branch, not `if` statements in `update()`.
- **Bosses spawn from a time table, not from the wave table.** `BossSystem.update(seconds)` fires each `BOSSES` entry once at `atSeconds`, then owns phases and moves. Phase selection is by HP ratio (first phase whose `hpAbove` is exceeded); 浴火重生 is a one-shot `rebirthAtHp` crossing guarded by `Enemy.bossRebornUsed` — without that flag the boss would be unkillable.
- **Boss drops live in `BossConfig`, not in `Enemy.drops`.** Bosses are not rolled, so "does it drop" is not a question; `GameScene.onEnemyKilled` reads the boss table for a boss and `enemy.drops` for an elite.
- **The boss HP bar is pulled, not pushed.** `UIScene.updateHUD` reads `bossSystem.bossHpRatio` / `phaseName` every frame, matching the HUD's pull-based contract — no event plumbing for a value that changes continuously.

### Debug panel (调试面板)

All developer tools live in the **pause menu** (`UIScene.addDebugPanel`), not on hotkeys. Keys fire at any time — including a mis-tap or an IME switch — and a run ruined by a stray F3 is worse than having no debug tool at all. The panel sits behind `DEBUG_PANEL_ENABLED` (`src/config/DebugConfig.ts`), which is `import.meta.env.DEV` — the call site is compiled away in a production build, and it was a hardcoded `true` that shipped enabled once, which is exactly why it is tied to the build mode now. The actions themselves are public `GameScene.debug*()` methods that return a one-line report, which the panel shows as a banner.

**Every new spell and every new monster must be reachable from this panel.** The rule, concretely:

- **Adding content is normally one config row, and that is enough** — the panel derives its lists from the tables, never from hand-written id arrays: `下一门神通` / `装满神通` iterate `Object.keys(SPELLS)`, `刷全部怪` iterates `Object.keys(ENEMIES)`, `下一个机制怪` filters `ENEMIES[*].mechanism`, `下一只首领` iterates `Object.keys(BOSSES)`, `凑齐融合` walks `EVOLUTIONS`. Do not enumerate ids in the panel; if you find yourself needing to, the config is missing a field, not the panel a branch.
- **If a new thing is NOT one config row away, it needs its own button.** A new pickup kind, a new world event, a new gating condition (e.g. an evolution, a realm gate) — anything you cannot reach by clicking the existing buttons gets an explicit action. *Content you cannot debug is content you cannot verify*, and unverified content is indistinguishable from broken content.
- **Reachability is checked at boot.** `GameScene.checkContentTables()` runs seven validators and `console.warn`s about anything unreachable: `validateSegmentWaves` (unknown ids / tier out of range), `validateEnemyReachability` (four spawn paths: wave weight, `mechanism`, `splitInto`, `boss`), `validateSpellReachability`, `validateEvolutionLinks`, `validateSpellKeys`, `validateEvolvedNotOffered` and `validateRelicReachability` (every exclusive relic must be some chain's `keyRelic`). Adding a row without a way to reach it fails loudly on the first run.
- New debug actions must refresh the HUD through `refreshHudAfterDebug()` — the UI is pull-based and only re-reads the systems on events.

### Elites and drops

- **Elites are randomly mutated normal enemies** (同阶修士), rolled by *time interval* (`ELITE_PERIOD_START` → `ELITE_PERIOD_END`), not fixed probability. A fixed chance fights the `SEGMENT_WAVES` spawn-interval curve, which compresses from 1.0s to 0.24s, and would make elites *denser* exactly when the screen is busiest.
- **An elite is ×30 HP, drops a 木匣 (wood chest) unconditionally, and never despawns** — instead `EnemyAiSystem` teleports it back to a 600px ring when it gets further than 1200px (so "run away from it" is not a strategy), and `MAX_LIVE_ELITES` caps how many can coexist. There is no 10:00 gate on chests any more: **without an early chest there is no early fusion**, and the chest *is* the fusion channel.
- **Six pickup kinds share one pool** (`Pickup` with a `kind` discriminant: `xp | relic | heal | xpPill | chest | bait | mimic`). A second pool would mean a second overlap registration and a second magnet loop; the magnet already works.
- **Overflow conversion means drops are never wasted**: a relic that cannot be taken (slots full / already maxed) converts to 30% of a level's XP. This is what removes the need for a discard UI.
- **A chest's quality rides on the pickup (`payloadId`), not on the pickup moment** — 木匣/玉盒/金匮 are three different textures so the player can judge whether the walk is worth it. 伪宝匣 deliberately wears the **gold** chest skin.
- `Pickup.lifeMs` despawn is mandatory — the old `XPGem` never expired, which is survivable without elites and fatal with them.

## Assets

There are **no binary assets checked in.** `src/utils/AssetGenerator.ts` draws every sprite at runtime with `Phaser.Graphics` + `generateTexture()`. Real art can be dropped into `src/assets/` — `src/utils/AssetLoader.ts` enumerates it with `import.meta.glob` at build time and **the filename is the texture key** (subdirectories are free). `AssetGenerator.makeTexture`'s `if (textures.exists(key)) return;` guard means a real file silently wins over the procedural one, so adding art needs zero code. Keys are convention-based (`enemy_${type}`, `elite_${type}`, `xp_gem_${tier}`, `pickup_relic` / `pickup_relic_${id}`, `pickup_chest_{wood|jade|gold}`, `proj_fireball|nine_nether_fire|jimie|huamo|sand|bolt|sword_array|enemy_shot`); an `ENEMIES` key and an `enemy_<key>` texture must share a name. **A misspelled filename has no error at all** — the game runs and that one creature just stays procedural — so `reportMissingAssets` prints the missing set at boot (grouped, because a typo and an unfinished asset look identical in a flat list) and the debug panel keeps a `素材 n/m` line on screen.

⚠️ **`PreloadScene` must keep its progress bar and `complete` handler inside `preload()`**, not `create()`. Phaser drains the queue after `preload()` returns, so a handler registered in `create()` never fires; the old code only worked because `load.start()` in `create()` kicked off a *second, empty* load whose `complete` fired by accident. That coincidence hides the bug the moment anyone adds a real file. A spell's `texture` and its `color` must also tell the same story — the projectile art is how a player reads which spell is coming at them, so a fire spell must not fire a purple orb (both 九幽火海 and 黄泉指 shipped that way once). Every spell texture matches its `SpellConfig.color`: 寂灭指 and 化魔指 are both violet but differ in *width* (the evolution's whole promise is "范围 ×5", so the projectile has to look it).

**Enemies only ever flip — there is no rotation, so four-view sheets are wasted.** `EnemyAiSystem`'s five approach branches all end in `e.setFlipX(dx < 0)`; nothing in the project calls `setRotation`/`setAngle` on an enemy. Monsters also **do not walk** — the walk animation was removed; they slide. What survives is frame *slicing*, `EnemyFrames.ensureEnemyFrames`, and it is not optional: real art in `src/assets/enemy_<id>.png` is an **equal-width horizontal strip**, and an unsliced strip renders **whole** — two monsters side by side for a 2-frame sheet. `Enemy.setup` therefore calls `showFirstFrame(this)` every time; that call is currently *idempotent insurance* rather than the only safeguard, because Phaser 3.19+ `Texture.add()` repoints `firstFrame` from `__BASE` at the first added frame (its stated purpose: "don't spam the display with entire atlases"), so `setTexture(key)` already lands on `_f0`. Don't build on that fallback — it is an internal guard, not the slicing contract; the invariant "one monster shows one cell" is what the explicit call states, and a pooled enemy is handed a different texture every time, so "which frame is displayed" has to be written back rather than inherited. **The real trap is that slicing failure is invisible in logs**: `getFrameNames()` excludes `__BASE` by default, so an unsliced texture looks exactly like a successfully sliced one — the only difference is on screen. Frame width is derived from `enemyTextureSize(cfg)`, not from the file, so a strip 3px off silently computes 1 frame and is left unsliced — degrading to a single frame on purpose, because art lands incrementally and the pipeline has to accept half-finished input. `elite_<id>` is sliced separately (elite is brightened + gold-outlined, not a tint of the normal frames). `AssetGenerator` draws **single-frame** procedural textures for exactly this reason. **`setFrame` on a name that doesn't exist logs a warning and leaves the sprite where it was**, so `showFirstFrame` guards with `tex.has(name)` first — otherwise every single-frame enemy logs a warning on every spawn. Frames are looked up through `enemy.scene.sys.textures`, never `enemy.anims`: `Sprite.anims` is an `AnimationState` whose `exists()` is literally `return (this.anims) ? this.anims.has(key) : false` over animations created by `anims.create()` on that sprite ("kept out of the global Animation Manager"), so anything built with `scene.anims.create()` is invisible to it. The same local/global split applies to `get()`; `stop()` and `play()` are state-level and unaffected.

## Mobile (PWA)

The production build *is* the mobile app: add-to-homescreen, fullscreen, offline. There is no native toolchain and no Capacitor dependency — `dist/` goes on any HTTPS static host.

- **`sw.js` is generated, never hand-written.** `scripts/vite-plugin-offline.mjs` reads the real (content-hashed) filenames out of the rollup bundle and inlines them as the precache list. A hand-written list goes stale on the very next build, and the symptom only appears once you are already offline and tapping the home-screen icon.
- **`putSafely` in that SW swallows its own errors on purpose.** `cache.put` rejects on redirect responses and on quota overflow; inside a `respondWith` promise an uncaught reject turns the *whole navigation* into a network error — a failed refresh becomes a dead site. Failing to write cache may only make things slower.
- **`registerOffline()` is `import.meta.env.PROD`-gated.** Caching dev-server module URLs means the next code edit appears to do nothing, which is worse to diagnose than having no offline support at all.
- **Icons are drawn, not committed.** `scripts/make-icons.mjs` is a dependency-free PNG encoder (zlib + a CRC table); `npm run icons` regenerates `public/icons/`. Same no-binary-assets rule as `AssetGenerator`.
- **`lockLandscape()` is allowed to fail.** Browsers only honour `screen.orientation.lock` in fullscreen, so the first call is expected to reject; it re-arms on the next touch. The real fallback is the `#rotate-hint` overlay in `index.html`, gated on `(orientation: portrait) and (pointer: coarse)` so a narrow desktop window never gets a full-screen blocker.
- **`autoPauseOnHide()` fires on `visibilitychange`.** Backgrounding a phone tab and alt-tabbing are the same gesture, and both freeze rAF — the resume delta is one enormous step. Without this the player is killed the instant they look away. Its guard must be `isPaused('GameScene')`, not `isActive('GameScene')`: a scene paused via `scene.pause()` (the death screen) still reports `isActive`.
- **Tap targets are sized for a 0.55× canvas.** `Scale.FIT` puts a 1280×720 design at roughly 0.55 scale on a phone in landscape, so the 44 CSS px minimum is **≈80 game px**. Anything below that was measured against a mouse. The debug panel's own layout bug is the cautionary tale: three columns × five rows put row 5 at y=722 on a 720-tall screen, so three debug buttons were off-screen and unclickable on *desktop* too.
- **Touch has no `pointerout`.** Phaser's `processUpEvents` emits only `UP`/`UP_OUTSIDE`, so anything hover-driven (relic tooltips) sticks on screen forever after a tap. It needs a `pointerdown` handler plus a scene-level dismiss, and the dismiss must let the object-level handler win — Phaser fires `GAMEOBJECT_POINTER_DOWN` before the scene's `POINTER_DOWN`.
- **A scene is only really stopped by `scene.stop()`.** `UIScene` is launched in parallel, so `GameScene` pausing or dying does not take it down; the HUD's pause button stayed tappable through the game-over screen until `onPlayerDeath` stopped it explicitly.
- **`localStorage` reads are wrapped in `SaveManager`.** iOS private mode throws `SecurityError` on access and quota overflow throws on write. `getBestTime()` runs inside `MainMenuScene.create`, so one uncaught throw there leaves a blank page rather than a lost high score.

## Rendering / camera

Fixed 1280×720 viewport with `Phaser.Scale.FIT` centered, over a **map-defined** world (`MapConfig.worldWidth/Height`, 3200² for 朱雀星). `pixelArt` + `antialias: false` + `roundPixels: true` are set globally. The ground is one `Graphics` object at `depth -100` drawn with a seeded LCG (`GameScene.createSeededRng`) so obstacles scatter deterministically — the same map looks identical every run, which is what lets a player build spatial memory of it. Camera follows the player with a deadzone, bounded to the world.

## Conventions

- Entity classes extend `Phaser.Physics.Arcade.Sprite` and call `scene.add.existing` / `scene.physics.add.existing` in their constructor.
- All tuning numbers live in `src/config/*.ts`. `XPSystem.computeXpToNext` is the highest-leverage knob — if pacing feels wrong, change it first.
- `SpellConfig` owns both the `SpellLevel`/`SpellDef` shapes and the `SPELLS` table (the type lives with the data because the table is the only producer).
- `vite.config.ts` sets `base: './'` and an `@` → `src` alias, but existing code uses relative imports; stay consistent with relative imports.
- Unused constructor params must be `_`-prefixed (`noUnusedParameters`).
